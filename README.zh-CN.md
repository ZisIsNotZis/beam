# beam

### llama.cpp 束搜索解码实验

**八个手写解码器，通过分叉模型的 KV 缓存同时保留多条候选续写，并记录下不同序列复用策略之间的取舍。**

**状态：** 已归档，不再维护 · 没有独立构建 · 绑定 2025 年初 llama.cpp 的内部示例 API · [AGPL-3.0-only](LICENSE)

---

## 为什么会有这个仓库

llama.cpp 自带的示例解码器一次只保留一条 token 流。束搜索需要同时保留多条
假设，而真正昂贵的不是采样，是 KV 缓存。每条存活假设都要有自己的序列；把一条
假设分叉成两条，就得复制或重映射这条序列，同时不能弄坏它的兄弟分支。

这些文件就是那次探索的工作记录。采样调用本身很普通，值得看的是几个决定：
什么时候复制 KV 序列，什么时候原地复用，什么时候连采样器状态也要一起克隆。
代码依赖的 llama.cpp 内部 API 后来已经变了，所以请把它当作一份带注释的设计
归档，而不是能直接用的库。

## 现在能做什么

- 为每个存活 beam 采样多个候选 token，去重后按累计对数概率对全局候选池剪枝。
- 在一个 `llama_context` 里维护多条假设，每条存活 beam 对应一个 KV 序列。
- 分叉时原地复用父序列，或者分配一条新序列并把父序列复制过去。
- 所有 beam 共用一个 sampler；采样器有状态时，也可以为每个 beam 克隆一份。
- 遇到结束 token 时输出完成的 beam，其余分支继续生成。
- 在一个 batch 里跑多个互不干扰的搜索（`beam3.cpp`），并打印 KV 占用和解码/
  规划耗时（`beam7.cpp`、`beam8.cpp`）。

这里**没有**：构建系统、公共 API、测试、基准、超出 llama.cpp common 参数的
CLI，以及对当前 llama.cpp 的兼容性。部分快照把 Qwen 对话模板写死在代码里，
后面的版本改用 `-p`。这些是归档的边界，不是未兑现的承诺。

## 快速开始

仓库本身没有可编译或可运行的目标。最快的入口是读这条演进线：

1. [`beam.cpp`](beam.cpp) —— 92 行，整个想法都在一个 `main` 里。
2. [`beam4.cpp`](beam4.cpp) —— 第一个干净的序列复用版本。
3. [`beam8.cpp`](beam8.cpp) —— 最后的分叉分配方案。

如果想在今天试用这套方法，把其中一个文件作为 `examples/` 目标放进 llama.cpp
源码树，并把 `llama_kv_self_*` 与 `common_sampler_*` 调用换成当前 API。
`beam4.cpp` 到 `beam8.cpp` 末尾保留了作者本地的编译命令；它们引用的是私有的
llama.cpp 和 BLAS 目录，应当当作来源记录，而不是操作步骤。

## 八个快照

| 文件 | 改了什么 | 得到的结论 |
| --- | --- | --- |
| [`beam.cpp`](beam.cpp) | 第一版。每个 beam 一个 sampler，分支冲突时复制 KV，写死 Qwen 对话提示。 | 主循环能跑，但逐个 beam 管理 sampler 和剪枝很快会变乱。 |
| [`beam2.cpp`](beam2.cpp) | 封装成 `BeamSearch`，记录 token 历史，分支数和 beam 宽度可配。 | 把搜索状态从 `main` 里拿出来，各个变体才方便比较。 |
| [`beam3.cpp`](beam3.cpp) | 用候选下标代替 beam 对象；多个独立搜索共享一个 batch 和连续序列槽。 | 批处理可行，但下标记录和槽位归属成了最难的部分。 |
| [`beam4.cpp`](beam4.cpp) | 共用一个 sampler，累加对数概率，原地复用供体序列，结束时输出 EOG 分支。 | 在早期方案里，这套序列重映射最干净。 |
| [`beam5.cpp`](beam5.cpp) | 把 `beam4` 接到 `-p`，并持续输出已完成的 beam。 | 只改驱动层，实验就能在那个 llama.cpp 版本上跑起来。 |
| [`beam6.cpp`](beam6.cpp) | 恢复逐 beam 的 sampler 克隆，但只在真正分叉时复制 KV。 | 采样器状态和 KV 状态的复制时机不同，必须分开处理。 |
| [`beam7.cpp`](beam7.cpp) | 用编译期开关选择是否克隆 sampler，整理分支重映射，加入 KV 和耗时统计。 | 同一套搜索代码就能比较两种采样器策略。 |
| [`beam8.cpp`](beam8.cpp) | 每次分叉都分配新的序列 id，不再复用供体槽位。 | 分支逻辑最简单，代价是更多 KV 复制。 |

`beam.cpp` 就是第 1 版，没有 `beam1.cpp`。编号就是想法被尝试的顺序，这些文件
保持原样，作为历史保留。

## 实现方式

后面的文件共用同一套模型：

```
prompt ── seq 0
            │
            ├── token A ── seq 0 ── ...
            ├── token B ── seq 1 ── ...   从 seq 0 复制 KV
            └── token C ── seq 2 ── ...   从 seq 0 复制 KV
```

- `BeamTok { sup, tok }` 是一棵只追加的 token 树。新候选指向父节点的下标；
  沿 `sup` 往回走就能还原一条假设。
- `Beam { seq, logit }` 是存活分支的末端：它占着哪条 KV 序列，累计分数是多少。
- `step()` 为每个存活 beam 采样候选，去重后按分数排序，移除结束的分支，为
  幸存者重映射或复制 KV 序列，再把下一批 token 放进同一个 batch。

`beam4.cpp` 到 `beam7.cpp` 原地复用获胜 beam 的序列，只复制其余分叉；
`beam8.cpp` 把每个额外分叉都复制进新序列，用更多 KV 工作换来更简单的归属规则。
采样器状态是另一条轴：共享、逐个克隆，或者像 `beam7.cpp` 那样在编译期二选一。

## 如何继续开发

仓库级没有构建。每个 `.cpp` 都是带 `main` 的编译单元，设计上要放在 llama.cpp
的 `common` 和 `sampling` 旁边。建议的循环是：

1. 选一个内部示例 API 与文件匹配的 llama.cpp 版本。
2. 把这个文件作为 `examples/` 目标加进那棵树。
3. 在临时副本里改；编号快照保持原样。
4. 如果要移植到今天的 API，改 KV 和采样器调用，不要改搜索结构——序列归属
   模型才是值得保留的部分。

这里没有 CMakeLists、包清单或测试框架。这是归档刻意划定的边界，不是漏发的
构建产物。
